# NEXI Capability and Execution Routing

Purpose: canonical NEXI project overlay for selecting skills, MCPs, CLIs, browser surfaces, and verification lanes. Global Worker-0 law and capability ownership live under `/home/mellonelay1999/RDC_ONBOARDING.md` and `/home/mellonelay1999/.agents/`; this file adds only NEXI-specific authority and routing. It does not authorize production mutation. Worker-0 capability lookup is delegated to `NEXI_WORKER0_CAPABILITY_INDEX.md`; detailed catalogs/guides are progressive-disclosure references, not startup reading.

## Dynamic routing model
Global control stack: `ChatGPT parent -> Selective Intelligence when triggered -> Agent Kernel durable governance -> Get-Fable lifecycle -> narrow capability owner -> Riqor evidence gate`.

NEXI execution overlay:
`OWNER MESSAGE -> COMPLETE TASK CONTRACT -> CURRENT NEXI AUTHORITY -> CORRECTION/DRIFT HANDLING WHEN REQUIRED -> TASK CLASSIFICATION -> ONE PRIMARY RESPONSIBILITY OWNER -> 0..N NON-OVERLAPPING SPECIALISTS -> FASTEST PRECISE TOOL/MCP/CLI -> EXECUTE -> FOCUSED VERIFY -> RIQOR FRESHNESS/COMPLETION GATE -> PARENT FAN-IN -> DURABLE STATE RECONCILIATION WHEN REQUIRED -> REPORT`

Compile the complete owner message before execution: required actions/evidence/sequencing, must-preserve state, explicit non-goals, mutation/production authority, completion conditions, and required documentation/state updates. Do not silently drop secondary requirements.

Do not maintain a second permanent catalog of every installed plugin, skill or version. `@skill`/plugin mentions are capability hints, not a mandatory reading queue: classify them as PRIMARY, SUPPORTING, or AVAILABLE-BUT-NOT-NEEDED. Discover or reread a skill/tool only when its operating contract can materially change the current task; reuse proven capability routing while unchanged.

## Authority and reuse
Current owner decision wins. GitHub `main` is durable source authority. Cloudflare Worker + Container is the only active backend execution/runtime authority; Worker 0 is not a parallel backend runtime. NestJS remains domain authority, D1 durable application/financial truth, Ledger accounting truth, EventOutbox publication boundary, and Aiven Valkey realtime/cache/Streams only. `PROVEN + UNCHANGED = REUSE`.
Third-party skills specialize work; they do not override NEXI architecture, security boundaries, or owner authorization.

## Responsibility owners
- Source/files: direct source, native RDC files/search, `rg`/`fd`/`ast-grep`.
- Graph/topology: Graphify local/cloud; paths/ownership/affected/blast radius, never behavioral proof.
- Semantic lookup: DeepWiki; cross-check consequential conclusions.
- Static/change risk: Fallow + CodeScene; add specialist static tools only for distinct risk.
- External docs: Context7 + current official vendor docs; current web research only when repo/runtime is not authority.
- Platform/backend runtime: current official Cloudflare docs first, then verified Wrangler/Cloudflare MCP/runtime surfaces; use Wrangler Container SSH when documented shell access is required. `avn` + `redis-cli` remain Valkey realtime/cache only. Never substitute a VM backend for Cloudflare runtime truth.
- Git/PR/CI: Git + GitHub.
- Runtime/telemetry: direct service/process/HTTP evidence, Sentry, task-relevant Cloudflare observability.
- Browser: local Playwright first; Polypane + Chrome DevTools MCP for responsive/DOM/network inspection; BrowserStack for real browsers/devices when materially justified.
- Direct bounded editing: parent/RDC when owner and proof are deterministic.
- Heavy workers: Codex/Kilo only for substantial bounded work or independent review where separate reasoning context adds value.

## Skill selection
Classify the task first. Select one primary skill/workflow owner for each responsibility, then only non-overlapping specialists. Do not activate duplicate planning, TDD, debugging, review, or parallelism owners simultaneously unless they have distinct jobs.
Use Selective Intelligence when a current owner correction, drift, repeated failure, duplicated authority, or reopened proven work requires realignment.
If the owner/path/procedure are already known, begin execution immediately. Do not spend the preflight rereading every mentioned skill, dumping whole tool catalogs, or rediscovering proven MCP/CLI capability. Tool availability is not an instruction to invoke everything and never expands mutation or production authority.

## Browser responsibility split
1. Playwright: deterministic local automation.
2. Polypane: responsive multi-viewport surface; CDP at `127.0.0.1:5858` when running.
3. Chrome DevTools MCP: inspect/control Polypane panes, DOM/accessibility, console/network, screenshots, input/navigation, performance/debugging.
4. BrowserStack: real-browser/device cloud, accessibility/cross-browser/visual/remote automation when local evidence is insufficient.
5. BrowserStack Local: only when cloud testing must reach localhost/private Worker-0 services.
6. VNC/noVNC: optional owner human-GUI/login lane only; never a browser automation dependency.

## Verification
Match proof to the claim: deterministic checks -> runtime observation -> source reconciliation -> independent review. A graph path does not prove behavior; a build does not prove runtime; browser success does not repair a source/contract failure.
Keep `IMPLEMENTED`, `STATICALLY_VALIDATED`, `TESTED`, `INTEGRATED`, `RUNTIME_VERIFIED`, `DEPLOYED`, and `OWNER_ACCEPTED` distinct.
