## Shared interaction and command rules

Use the Public wallet session for personal operations and the Admin session plus the effective permission for operator operations. Backend guards and ownership checks govern both. For economic requests hold the original key with the actor, account, amount, asset and action. Where the UI implements durable pending intent, preserve this binding across reload. Display pending while awaiting a response. A timeout leaves the outcome unknown. Reconcile by original key or durable ID, compare terms, and retry only through the supported replay path. Render explicit rejection as rejection. Display precise amounts with asset and scope. After commit, authoritative REST readback proves the economic result. Socket and queue messages can drive invalidation. See [financial recovery contracts](../security/NEXI_FINANCIAL_INTEGRITY_REQUIREMENTS.md#financial-command-lifecycle-and-recovery-contracts).

## D01 Wallet authentication and onboarding

[Login](../../frontend/app/login/page.tsx) and the [wallet SIWE flow](../../frontend/app/lib/wallet-siwe.ts) connect the chosen provider, show the account, obtain the server challenge and sign once. [AuthController](../../backend/src/auth/auth.controller.ts) accepts challenge and verify inputs and delegates SIWE message, nonce, origin, signature and Ethereum chain 1 checks to [WalletAuthService](../../backend/src/auth/wallet-auth.service.ts). Customer identity, profile/referral and scoped wallet reads come from the persisted user, wallet identity and authenticated session. Returning users retain existing state. Wrong chain, absent provider, rejected signature and expired session bring the customer back to the appropriate choice. Account change must isolate old identity data before loading the new session. Ordinary product actions reuse the authenticated session. Admin sign-in is independent. See [J01](#j01-wallet-onboarding) and [J17](#j17-recovery-and-consistency).

## D02 Wallet accounts balances and Activity

[Wallet](../../frontend/app/dashboard/wallet/page.tsx) exposes Funding/MAIN, Spot, Margin, Options/BINARY and Finance, with Deposit, Withdraw, Transfer and Convert. [WalletController](../../backend/src/wallet/wallet.controller.ts) owns /wallet/overview, /wallet/me, /wallet/currencies/list, /wallet/activity and scoped Ledger reads. User, cursor, scope and filters distinguish the correct records. Available, locked, committed, liabilities and estimated portfolio value are separate. Market instruments do not define custody support. An enabled zero-balance account differs from an unsupported asset. After a command refresh affected scopes and Activity by reference; during a failed refresh preserve context with its freshness status. Admin Ledger reads subject and posting IDs independently. See [J04](#j04-wallet-asset-and-portfolio), [J07](#j07-transfers) and [J17](#j17-recovery-and-consistency).

## D03 Deposits and withdrawals

**Deposits.** [Deposit sheet](../../frontend/app/dashboard/wallet/components/DepositModal.tsx) loads eligible addresses and networks from /financial/deposit-destinations. Proof intent, upload authorization and claim submission are separate operations. [FinancialOperationsService](../../backend/src/financial/financial-operations.service.ts) validates scoped proof keys, type/size and stored evidence. Admin review and credit use reasons and original keys. Approval or upload is distinct from a posted Funding credit. The only implemented observation provider is `deterministic-test`; no production chain observer, webhook/worker or transaction confirmation adapter is present in Backend source. A manual claim can currently be Admin-credited without a linked verified observation (`txHash` is optional and `linkedObservedDepositId` is not required by the credit writer). Therefore proof/review/ledger workflows exist, but real incoming chain deposits are not reconciled to verified ownership, transaction identity and confirmations. That is a confirmed source gap; production provider/custody configuration and authority are also absent from the inspected source. Do not treat an Admin credit as chain proof.

**Withdrawals.** [Withdraw sheet](../../frontend/app/dashboard/wallet/components/WithdrawModal.tsx) uses capabilities and /financial/withdrawals. Independent sensitive authorization precedes the request. The service validates asset/network limits, amount, destination and immutable replay terms, then reserves amount plus fee. Admin review, approval, rejection and release are separate. Approval is not an external withdrawal: no production submit/status/finality adapter or chain reconciliation worker is present in Backend source; `providerLive:false`, and settlement accepts only deterministic-test receipts. Implemented request/reservation/review remains usable, while external transaction identity, finality, failure and release reconciliation are a confirmed source gap. Provider/custody authority and configuration are not present in the inspected source. Show gross, fee, net and status separately; recover ambiguous acknowledgement by request key. Do not represent approval as blockchain completion. See [J05](#j05-deposit-proof-and-credit), [J06](#j06-withdrawal-review-and-recovery).

## D04 Transfers and Convert

[TransferModal](../../frontend/app/dashboard/wallet/components/TransferModal.tsx) distinguishes same-owner scope movement using WalletAccountTransferDto from recipient transfer using Gate2TransferDto. The gateway pairs debit and credit, rejects invalid ownership, insufficient balance or changed replay terms, and records posting IDs, audit, Activity and an outbox event. Same-owner recovery checks Activity by key and correlation; recipient mode reads /financial/transfers with the original key. Admin independently reads the postings.

[ConvertModal](../../frontend/app/dashboard/wallet/components/ConvertModal.tsx) reads eligible pairs and requests a quote for direction and amount, then separately accepts its ID and terms. The backend validates owner, expiry and acceptance replay, and posts both asset legs. Zero separate commission allows a spread. A stale or expired quote requires new terms and review. An ambiguous acceptance uses the original quote/Activity and balances. See [J07](#j07-transfers), [J08](#j08-convert).

## D05 Binary Options

[Options](../../frontend/app/dashboard/binary/page.tsx) loads /binary/config and accepts pair, duration, payout/limits, direction and stake. OpenBinaryPositionDto carries the original key. Insufficient funding should offer an explicit Funding/Options path while preserving valid input, without resubmission. Bind countdown and entry price to the returned position. [BinaryService](../../backend/src/binary/binary.service.ts) resolves approved expiry authority, leaves stake reserved on delayed settlement and delegates atomic WIN/LOSS finalization with position, configuration/research version and price provenance. ERROR is separate from economic LOSS. Current and history routes and the Admin trading/settlement views reconcile the same position. Research controls are isolated, versioned and audited. The provider comparison treats equal entry and expiry as LOSS. DRAW or REFUND would require a separately approved policy and source support. See [J09](#j09-binary-options).

## D06 Spot

[Spot](../../frontend/app/dashboard/spot/page.tsx) shows pair, available base/quote, estimated cost and review. [SpotController](../../backend/src/spot/spot.controller.ts) dispatches PlaceOrderDto and cancel DTOs to SpotService. A replay compares the original terms before reevaluating moving market inputs. Reserve before execution, persist order and fill IDs, and account for actual cost, fee asset and residual reserve separately from requested notional. A partial fill keeps only the remainder reserved. Cancellation preserves earlier fills. Treat minimum size, invalid quantity, insufficient balance, stale quote and unsupported stop behavior according to current backend policy. Read /spot/orders/by-intent on timeout; refresh open/history and trades. Admin order/cancel and Ledger readbacks use the same IDs. Provider trades/depth are reference data. See [J10](#j10-spot).

## D07 Isolated Margin

The [Spot/Margin surface](../../frontend/app/dashboard/spot/page.tsx) displays readiness, collateral, debt, exposure and equity independently. [MarginController](../../backend/src/spot/margin.controller.ts) handles keyed open, close, liquidation, pending cancellation, transfer and unmatched-borrow repay. MarginService enforces ownership, leverage and risk, and the local gateway owns margin ledger/position transitions. Entry may be PENDING before OPEN. Close or liquidation can remain CLOSING awaiting the original exit fill. Recovery compares owner, exit order, key and liquidation intent; reconcile realized P&L, debt repayment, collateral release and Activity before displaying terminal state. Admin exposure and risk projections are reads. See [J11](#j11-isolated-margin).

## D08 Finance Earn Mining and Loans

[Mining](../../frontend/app/dashboard/mining/page.tsx) reads active plans/subscriptions and uses MiningSubscribeDto with a keyed amount and separate redeem/cancel actions. Admin creates, edits, enables and disables plans. Seven total plans are allowed, including disabled plans; the authoritative SQLite create statement counts every row, and the Prisma fallback enforces the same cap inside its transaction. The Admin page displays the total and disables only creation at the cap, leaving edits available. [MiningService](../../backend/src/mining/mining.service.ts) validates plan state, bounds and original terms; a typed pre-write stale-plan conflict lets Public clear only that known nonfinancial intent and reload the catalog. The gateway/workflow owns the immutable accepted plan snapshot, Finance reserve, reward accrual and settlement. Plan visibility alone cannot establish entitlement. Current source implements Admin-configured fractional **daily** `dailyYield` and UTC daily accrual; historical example rates do not establish mandatory platform defaults. Pending redemption, expiry, reward posting and Public/Admin readbacks must distinguish available funds from commitments.

[Loans](../../frontend/app/dashboard/loans/page.tsx) uses ApplyLoanDto with configured plan, amount, duration, collateral details and document reference, and a keyed repayment DTO. [LoanService](../../backend/src/loans/loans.service.ts) enforces original terms and plan currency/bounds. Admin plan reads include disabled plans and the editor can reactivate/deactivate a plan; Public continues to receive active plans only. Application, Admin decision, disbursement, debt, interest, repayment and overdue state are distinct. Admin review precedes disbursement. Read /loans/applications/by-intent after ambiguous submission. Reconcile LoanApplication, repayment and Ledger/Activity with the Admin action. LoanService applies configured `interestRate` once to principal for the selected `durationDays`; collateral valuation and customer-facing rate presentation require separate evidence, not a new blanket owner decision. See [J12](#j12-mining-and-earn), [J13](#j13-loans).

### D02 / J04 — Wallet scopes and authoritative readback

- **Actor/UI:** authenticated Public wallet; Funding/MAIN, SPOT, MARGIN, BINARY/Options and FINANCE are separate scopes. Market instruments and deposit networks are independent catalogs.
- **Read contract:** `WalletController_getOverview` GET `/wallet/overview`, `WalletController_getMyWallet` GET `/wallet/me`, `WalletController_getMyLedger` GET `/wallet/me/ledger`, and `WalletController_getActivity` GET `/wallet/activity`; Public JWT/AuthSurface guards apply to customer-scoped reads. `WalletService` delegates balances and ledger reads to the configured financial authority. Overview distinguishes account existence and scope; monetary values are string-valued.
- **Ownership/persistence:** authenticated principal and requested scope/filter determine the read. LedgerAccount is unique by user, asset and scope; available and locked balances are separate. ### D03 / J06 — Withdrawal capabilities, reservation and operator decision

### D04 / J07 — Account movement and recipient transfer

### D04 / J08 — Convert quote and acceptance

- **Actor/UI/API:** `FinancialOperationsController_conversionPairs` GET `/financial/conversion/pairs`; `_quote` POST `/financial/conversion/quote`; `_accept` POST `/financial/conversion/accept`. All are authenticated Public operations. Quote DTO binds source/destination assets, exact amount and quote key; accept DTO binds quote ID and separate acceptance key.
- **Policy/state:** distinct assets and eligible configured/live market pair are required. Quote persists rate, source/evidence, configuration version and TTL (default 30 seconds where unset). Acceptance requires an owned OPEN, unexpired quote; original acceptance key may replay the accepted intent, changed terms/key or expired/ineligible quote reject. The rate is a quote input, not proof of guaranteed execution price.
- **Persistence/readback:** acceptance delegates the two asset legs to the financial command gateway; refresh source/destination scopes and Activity using the original quote/acceptance identity. On timeout read the original quote/result and never create a fresh acceptance key blindly. Legacy `/conversion/rate`, `/conversion/convert` and admin rate controller paths are retired (410) and must not be presented as active.

### D05 / J09 — Binary (Options) lifecycle and settlement

- **Actor/API:** public config GET `/binary/config`; authenticated Public POST `/binary/position` (`OpenBinaryPositionDto`), POST `/binary/settle` (`SettleBinaryPositionDto`), GET current/history positions. Admin config and position/settlement routes require effective Admin permission; inventory is in the API map.
- **Open:** service validates positive USDT stake, active pair, enabled versioned configuration, duration and min/max, and approved quote; replay binds owner, pair, direction, duration and stake. It captures entry quote identity/provenance and delegates opening/reserve to the command gateway.
- **Settlement:** expiry processing uses the stored pair and exact configuration version plus approved expiry quote. Missing eligible pair/config/quote produces retryable `SETTLEMENT_DELAYED` and retains locked stake. Atomic settlement records payout/realized result with position identity, request correlation and expiry quote provenance. WIN/LOSS are economic outcomes; technical ERROR/delay is not LOSS. Terminal history is distinct from current positions.
- **Consumer/recovery:** Public reconciles current/history snapshots with newer socket versions and re-fetches after reconnect. Binary socket requires JWT and active Public auth session; user/session rooms are scoped. Admin settlement requests authoritative settlement and does not choose the outcome; research override is limited to approved open research position/version.
- **Settled owner policy:** Binary's only economic outcomes are WIN and LOSS, and equal entry/expiry price is LOSS. No DRAW/refund result is authorized. Retryable settlement delay and technical ERROR are different from economic LOSS; reconcile the original position, prices and Ledger before claiming an outcome.

### D06 / J10 — Spot order, execution and cancellation

- **Actor/API/DTO:** Public POST `/spot/order` (`PlaceOrderDto`) and POST `/spot/cancel` (`CancelOrderDto`) require JWT/Public surface. Private reads include keyed `GET /spot/orders/by-intent`, `/spot/orders/open`, `/spot/orders/history`, owned order and trade history. DTO money inputs are decimal strings up to 18 fractional digits; keys are bounded strings. API IDs and consumers are listed in the operation map.
- **Open/reserve:** source resolves original intent before reevaluating live quote/protection and rejects changed terms. Pair, fee, quote and market protection are checked; BUY reserves quote including applicable fee, SELL reserves base quantity. Matcher is bounded; unmatched market remainder is cancelled after processing.
- **Execution/state/readback:** order requested amount/notional, filled amount, actual execution value, fee asset and remaining reserve are separate values. Partial fill retains only the unexecuted reserve; cancellation does not erase prior fills. Read by original intent after timeout, then refresh open/history/trades and compare durable IDs. Public persists pending intent before POST and blocks a new order while the result is unknown; failed local cleanup keeps the lock.
- **Market-data distinction:** `/market/depth` and `/market/trades` are provider reference data; `/spot/orderbook` and `/spot/market-trades` are internal matcher views. Public Spot consumes provider REST and `/market` socket events, validating provider/source/version/instrument/freshness; it resnapshots and recovers sequence gaps. These feeds are not interchangeable.
- **Admin:** `spot.view` gates the route; `spot.cancel_order` gates cancel. Unknown status is excluded from ordinary open/cancel action. Pausing pair blocks new orders without auto-cancelling open orders. Adapter hard-coded display defaults are not proof of backend trading configuration parity.

### D07 / J11 — Isolated Margin lifecycle

- **API/actor:** Public authenticated quote, list, open, exit-intent, pending cancel, close, liquidate, mark, MAIN↔MARGIN transfer, orphan-borrow repay and activity operations are in `MarginController`; route/DTO/guard matrix is linked from the API operation map. Inputs normalize pair/assets and use decimal strings (up to 18 places), integer leverage and 8–160 character keys; service allow-list/config can be narrower than DTO bounds.
- **Open:** USDT-only same-owner MAIN↔MARGIN transfer is a paired ledger movement. Open binds the exact intent; service calculates quantity using collateral×leverage/live quote rounded down to 18 decimals. Long debt is collateral×(leverage−1); short debt is quantity. It reserves a MARGIN-scoped Spot order with borrow metadata. Position stays PENDING until entry order fills; exact retry recovers original order/borrow and rejects changed terms.
- **Close/liquidate/recovery:** one close order is persisted; position can remain CLOSING until matching order fills. Then service settles PnL and principal+interest. Liquidation uses configured maintenance threshold. Exit-intent lookup and original idempotency key recover uncertain close/cancel. Activity and position history are authoritative readbacks, not socket status.
- **Schema:** LedgerAccount tracks available/locked per owner/asset/scope; SpotMarginPosition records collateral, quantity, debt, PnL, state, open key and entry/close orders; events/activity have unique intent keys; LedgerPosting uses exact decimal strings and unique account/key. See `backend/src/prisma/d1-client/schema.prisma:1147-1273`.
- **UNKNOWN:** interest-accrual scheduler/caller, annual rate units, exact maintenance policy value and full command transaction boundary remain unresolved in this slice.

### D08 / J12 — Mining/Earn subscription and accrual

### D08 / J13 — Loan application, decision and repayment

Actor submits one command with its identity and key → response is lost/delayed/duplicated or transport reconnects → client marks UNKNOWN and blocks changed/new intent → owner-scoped API reads by original key/ID → correlate durable state, Ledger postings and applicable audit/outbox → refresh Public and Admin projections → display returned pending/rejected/completed/unresolved state. Retry only identical terms under the existing idempotency rule; changed terms require a resolved prior intent. Socket/BullMQ events prompt reads but do not settle balances. No global exactly-once delivery claim is made.

### J18 implementation detail — Economic and release acceptance journey

Reviewer starts with frozen criterion ID/wording → separates desired result from actual implementation → maps Public/Admin/API/source/schema owners → uses approved evidence method in identified build/deployment/runtime → follows intent to durable account/posting/state/audit and visible readback → records result, revision, environment, artifact, actor, time and evidence path → independent review checks it. Source match, graph path, test receipt or API inventory cannot mark browser/customer/release acceptance. This campaign ran none of those acceptance actions; pre-campaign statuses remain intact.
