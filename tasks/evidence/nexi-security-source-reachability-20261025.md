## Source-path reachability and advisory preconditions

**Public Sentry — GHSA-mchm-gjx6-7h55 (critical): not demonstrated.** `frontend/next.config.js` wraps the config with `withSentryConfig`, and `frontend/instrumentation.ts` plus `frontend/instrumentation-client.ts` import `@sentry/nextjs`, so the SDK is source-reachable and present in the deployed shared store. The advisory affects versions below `10.75.2` but requires `tunnelRoute`, a Webpack build, an application route under that tunnel path, and middleware as the sole authorization layer ([official advisory](https://github.com/advisories/GHSA-mchm-gjx6-7h55)). No `tunnelRoute` is configured in source or deployed `next.config.js`. The deployed `.next/routes-manifest.json` has no rewrites; `.next/server/middleware-manifest.json` has no middleware entries. The route condition is therefore not demonstrated for the observed source/artifact. The installed version remains in the affected version range; generic SDK tunnel code alone is not evidence that NEXI configures it.

**Backend Nest 12 / platform-express — no independent Nest high path demonstrated.** `backend/src/main.ts` uses `NestFactory.create(AppModule)` with the Express platform. No `@nestjs/platform-fastify` or `@nestjs/microservices` package is in the resolved lock graph; source search found no `createMicroservice`, `connectMicroservice`, or `Transport.TCP` usage. The high Nest microservice advisory GHSA-m8vh-jmq9-5rjg applies to `@nestjs/microservices` below `12.0.2` when its TCP or RabbitMQ transport is used; the observed Nest packages are `12.0.3`, and the affected package/transport path was not found ([official advisory](https://github.com/nestjs/nest/security/advisories/GHSA-m8vh-jmq9-5rjg)). The other reviewed Nest high middleware-bypass advisory GHSA-9c5c-9qcx-q35q is for `@nestjs/platform-fastify`, which is absent ([official advisory](https://github.com/nestjs/nest/security/advisories/GHSA-9c5c-9qcx-q35q)). In this graph, `@nestjs/platform-express` is relevant because it brings the Multer dependency below.

**Multer — GHSA-q7qp-rjg7-q26m (high): conditionally reachable.** `backend/src/admin/admin.controller.ts:129` and `backend/src/communications/communications.controller.ts:108` call `FileInterceptor` for upload routes. Both set file-size and file-count limits; neither supplies `fileFilter`. The emitted counterparts under `/srv/nexi/backend/dist/src/{admin/admin.controller.js,communications/communications.controller.js}` show the same interceptor options. A repository search found no `MulterModule` registration or `fileFilter`. The advisory affects Multer `<2.5.0` only when configured with an **asynchronous** `fileFilter` and a request teardown races a pending callback ([official advisory](https://github.com/advisories/GHSA-q7qp-rjg7-q26m)). The upload paths and vulnerable package version are present, but that required trigger is not demonstrated in inspected source or emitted code. Size/count limits do not change the advisory condition.

**`ws` — GHSA-96hv-2xvq-fx4p (high): not demonstrated on the inspected inbound server path; vulnerable versions remain in the lock graph.** The advisory affects `ws` 8.x below `8.21.0` when a peer sends many small fragments/chunks to a `ws` receiver ([official advisory](https://github.com/advisories/GHSA-96hv-2xvq-fx4p)). Backend source `backend/src/market/binance-spot.adapter.ts:90` creates a client `WebSocket` for the outbound Binance stream. The server-side Socket.IO/Engine.IO package at `/srv/nexi/backend/shared/node_modules/engine.io/build/server.js` imports `ws` and uses its server implementation; a Node 24 `createRequire` resolution probe anchored there resolves root `ws@8.21.0`, the patched version. The nested `socket.io-adapter/node_modules/ws@8.18.3` is imported by `in-memory-adapter.js` for `Sender.frame` pre-encoding of outbound frames, not an observed receiver; `engine.io-client`'s nested copy is in its client transport. A nested `viem` copy is also present but its application call path was not traced here. Thus the audit's affected package copies are real, while an affected `ws` receiver on NEXI's inspected server ingress was not demonstrated. This does not clear the dependency audit.
