## Wallet authentication rate limiting

**CONFIRMED — FIXED in working tree.** The public SIWE challenge and verification handlers had no rate-limit guard. The existing Redis-backed authentication guard was available from `AuthModule`, but bootstrap did not configure Express proxy trust: adding its IP limit alone would group clients behind Nginx under the proxy address. The live API listener was observed on `127.0.0.1:3002`; the active API Nginx vhost forwards to it and appends the peer address to `X-Forwarded-For`. The source now trusts loopback proxies and applies separate 20-request/60-second IP buckets for wallet challenge and verification. Existing wallet messages, nonce consumption, signature verification and Public request/response bodies remain unchanged. This source change also affects `request.ip` on other routes; it trusts loopback connections, so a local process able to connect directly to the API can supply forwarded headers. The release owner must verify the actual proxy topology before deployment.

NestJS 12.0.3 / Express 5.2.1: [NestJS rate limiting behind proxies](https://docs.nestjs.com/security/rate-limiting#proxies), [Express proxy trust](https://expressjs.com/en/guide/behind-proxies/). The installed NestJS patterns skill's applicable rule is to bind guards at the controller boundary and verify them at request level; the API design skill's rule is to preserve existing request and response contracts.
